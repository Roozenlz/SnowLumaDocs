On Linux, SnowLuma runs **only via Docker**. The image bundles Linux QQ + Xvfb + VNC + noVNC + supervisord + the SnowLuma `lite` distribution, so the host needs nothing beyond Docker.

The build inputs (`Dockerfile`, `start.sh`, `supervisord.conf`, `docker-compose.yml`) live in the main repo's [`docker/`](https://github.com/Roozenlz/SnowLuma/tree/main/docker) directory, and the build runs in that repo's own GitHub Actions — no external repository involved.

## Image

| Item | Value |
| --- | --- |
| Image | `roozen/snowluma:latest` (or a specific tag, e.g. `:v2.4.3`) |
| Arch | `linux/amd64`, `linux/arm64` |
| Base | `node:22-bookworm-slim` |
| Bundled | Linux QQ, Xvfb, VNC, noVNC, supervisord, SnowLuma `lite` |

The image does **not** rebuild SnowLuma — it consumes the prebuilt `lite` tarball from each GitHub Release, so the release and the image build are decoupled.

### Tag policy

| Tag | Published by | Notes |
| --- | --- | --- |
| `latest` | `release.yml` | Moves only with **stable** tags (no `-` in the tag name); always the newest formal release. |
| `v2.4.3` | `release.yml` | One per tag, matching the GitHub Release 1:1. |
| `dev` | `dev-build.yml` | Rolling rebuild on every push to `dev`; `linux/amd64` only. |
| `dev-<sha>` | `dev-build.yml` | Immutable snapshot of the same build, for pinning and rollback. |

Treat `dev` images as integration builds, not production deployments.

## Ports

| Port | Purpose |
| --- | --- |
| `5900` | VNC (remote desktop — needed to scan-login QQ) |
| `6081` | noVNC (browser VNC, no client needed) |
| `5099` | SnowLuma WebUI |
| `3000` | OneBot HTTP (default) |
| `3001` | OneBot WebSocket (default) |

## Host setup: relax the ptrace policy

<Callout type="warn">
**Do this before starting the container, otherwise hook injection will fail at runtime.**
</Callout>

SnowLuma's native addon uses `ptrace` to inject the hook into the in-container QQ process. Modern Linux distros (Ubuntu / Debian / Arch / …) ship with `kernel.yama.ptrace_scope` set to `1` or higher, which means **even with `--cap-add=SYS_PTRACE` on the container, the host kernel still blocks the ptrace call**.

Run **once** on the host:

```bash
echo 'kernel.yama.ptrace_scope=0' | sudo tee /etc/sysctl.d/99-snowluma-ptrace.conf
sudo sysctl --system
```

Verify:

```bash
sysctl kernel.yama.ptrace_scope
# expected: kernel.yama.ptrace_scope = 0
```

Writing to `/etc/sysctl.d/99-snowluma-ptrace.conf` keeps the setting across reboots. If your host has stricter security requirements (multi-tenant, internet-facing), prefer a dedicated isolated host (bare metal / VM) over relaxing the system-wide policy.

## One-line docker run

```bash
docker run -d \
  --name snowluma \
  --restart unless-stopped \
  --shm-size=1g \
  --cap-add=SYS_PTRACE \
  --security-opt seccomp=unconfined \
  -e VNC_PASSWD=vncpasswd \
  -p 5900:5900 \
  -p 6081:6081 \
  -p 5099:5099 \
  -p 3000:3000 \
  -p 3001:3001 \
  -v snowluma-data:/app/snowluma-data \
  -v snowluma-qq-config:/app/.config \
  -v snowluma-qq-data:/app/.local/share \
  roozen/snowluma:latest
```

<Callout type="warn">
`--cap-add=SYS_PTRACE` and `--security-opt seccomp=unconfined` are **mandatory**. SnowLuma's native addon uses ptrace to inject the hook into the QQ process; the default seccomp profile blocks that.
</Callout>

`--shm-size=1g` is needed for QQ's Chromium runtime — the default container `/dev/shm` is too small and QQ will crash.

## docker-compose

Recommended over `docker run`. The main repo already ships [`docker/docker-compose.yml`](https://github.com/Roozenlz/SnowLuma/blob/main/docker/docker-compose.yml) — use it as-is.

```yaml
services:
  snowluma:
    image: ${SNOWLUMA_IMAGE:-roozen/snowluma:latest}
    container_name: ${SNOWLUMA_CONTAINER:-snowluma}
    restart: unless-stopped
    shm_size: 1gb
    cap_add:
      - SYS_PTRACE
    security_opt:
      - seccomp=unconfined
    environment:
      VNC_PASSWD: ${VNC_PASSWD:-vncpasswd}
      SNOWLUMA_UID: ${SNOWLUMA_UID:-1000}
      SNOWLUMA_GID: ${SNOWLUMA_GID:-1000}
      SNOWLUMA_WEBUI_HOST: ${SNOWLUMA_WEBUI_HOST:-0.0.0.0}
      SNOWLUMA_WEBUI_PORT: ${SNOWLUMA_WEBUI_PORT:-5099}
      SNOWLUMA_LOG_LEVEL: ${SNOWLUMA_LOG_LEVEL:-info}
      SNOWLUMA_SCREEN: ${SNOWLUMA_SCREEN:-1920x1080x24}
      SNOWLUMA_HOOK_AUTOLOAD: ${SNOWLUMA_HOOK_AUTOLOAD:-1}
    ports:
      - "${VNC_PORT:-5900}:5900"
      - "${NOVNC_PORT:-6081}:6081"
      - "${SNOWLUMA_WEBUI_HOST_PORT:-5099}:${SNOWLUMA_WEBUI_PORT:-5099}"
      - "${ONEBOT_HTTP_PORT:-3000}:3000"
      - "${ONEBOT_WS_PORT:-3001}:3001"
    volumes:
      - snowluma-data:/app/snowluma-data
      - snowluma-qq-config:/app/.config
      - snowluma-qq-data:/app/.local/share

volumes:
  snowluma-data:
  snowluma-qq-config:
  snowluma-qq-data:
```

Start (from the repo root):

```bash
docker compose -f docker/docker-compose.yml up -d
```

Upgrade:

```bash
docker compose -f docker/docker-compose.yml pull
docker compose -f docker/docker-compose.yml up -d
```

To track one specific version, pin it in `.env`:

```bash
SNOWLUMA_IMAGE=roozen/snowluma:v2.4.3
```

## Environment variables

| Var | Default | Notes |
| --- | --- | --- |
| `VNC_PASSWD` | `vncpasswd` | VNC / noVNC login password. **Change this**, otherwise anyone can see your QQ desktop. |
| `SNOWLUMA_UID` | `1000` | uid of the in-container `snowluma` user. Match it to the host owner of your mounted volumes. |
| `SNOWLUMA_GID` | `1000` | gid of the in-container `snowluma` user. |
| `SNOWLUMA_WEBUI_HOST` | `0.0.0.0` | WebUI bind address. The binary itself binds loopback only; the image opens it up, otherwise the published port can't reach it. |
| `SNOWLUMA_WEBUI_PORT` | `5099` | WebUI listen port (inside the container). |
| `SNOWLUMA_LOG_LEVEL` | `info` | `error` / `warn` / `info` / `debug`. |
| `SNOWLUMA_SCREEN` | `1920x1080x24` | Xvfb resolution + color depth. |
| `SNOWLUMA_HOOK_AUTOLOAD` | `1` | Image opts into auto-injection by default. Set `0` to fall back to the manual Load workflow. |
| `SNOWLUMA_QQ_FLAGS` | empty | Extra flags appended to the QQ command line, space separated. On GPU-less hosts try `--disable-gpu --disable-software-rasterizer`. |
| `SNOWLUMA_EXTRA_QQ_HOMES` | empty | Extra QQ account `HOME` directories, comma or space separated; each one gets its own supervisord program. See [multiple accounts](#running-multiple-qq-accounts). |

Environment variables override `runtime.json`, so they're the ergonomic knob in Docker.

## Volumes

| Volume | Container path | Contents |
| --- | --- | --- |
| `snowluma-data` | `/app/snowluma-data` | SnowLuma config, cache, SQLite. Includes `config/onebot.json` and `config/runtime.json`. |
| `snowluma-qq-config` | `/app/.config` | QQ client config. |
| `snowluma-qq-data` | `/app/.local/share` | QQ user data (login state, cache). |

**Don't delete these on upgrade** — you'll lose login state and configuration.

## First-time login

1. Open `http://<host>:6081/` (noVNC) and enter `VNC_PASSWD`.
2. Inside the remote desktop you'll see QQ already running. Scan the QR to log in.
3. Once login completes the hook auto-switches from passive observation to working mode — no need to click Load in the WebUI.
4. Open `http://<host>:5099/` for the SnowLuma WebUI.

### Finding the WebUI bootstrap password

On a fresh data volume the first launch logs a one-time password:

```bash
docker logs snowluma 2>&1 | grep -E "临时密码|initial credentials" | tail -n 1
```

Just the password string:

```bash
docker logs snowluma 2>&1 | \
  sed -nE 's/.*(临时密码: |initial credentials: user=admin password=)([^[:space:]]+).*/\2/p' | tail -n 1
```

<Callout type="info">
The bootstrap password is logged **only on a brand-new data volume's first boot**. Reusing the volume or restarting won't regenerate it.
</Callout>

## Running multiple QQ accounts

Linux QQ ships a single-instance lock — clicking the QQ icon again on a desktop that already has one running just focuses the existing window, it doesn't start a second process. The lock file lives at `$HOME/.config/QQ/SingletonLock`, so every instance needs its **own `HOME`**.

SnowLuma needs no extra configuration: [HookManager](https://github.com/Roozenlz/SnowLuma/blob/main/packages/bridge/src/hook-manager.ts) walks every QQ main process it can find, injects the hook into each, and spins up a separate `OneBotInstance` per UIN with its own `config/onebot_<uin>.json`.

### Declare them with `SNOWLUMA_EXTRA_QQ_HOMES` (recommended)

List the extra `HOME` directories and supervisord manages one QQ process per entry — a crash restarts **only that account**, leaving the others untouched:

```yaml
services:
  snowluma:
    environment:
      SNOWLUMA_EXTRA_QQ_HOMES: /app/qq-acct2,/app/qq-acct3
    volumes:
      - snowluma-data:/app/snowluma-data
      - snowluma-qq-config:/app/.config
      - snowluma-qq-data:/app/.local/share
      - snowluma-qq2:/app/qq-acct2     # second account's full HOME
      - snowluma-qq3:/app/qq-acct3     # third account

volumes:
  snowluma-data:
  snowluma-qq-config:
  snowluma-qq-data:
  snowluma-qq2:
  snowluma-qq3:
```

Separate paths with commas or spaces. The leading `/app` (primary account) is skipped automatically; duplicates and relative paths are ignored with a message in the log. Missing directories are created at startup.

After boot, `docker logs snowluma` prints something like:

```text
supervisord: 3 QQ program(s), no extra flags, config: /etc/supervisord.run.conf
```

Each account becomes a `[program:qq-<dirname>]` you can inspect individually:

```bash
docker exec snowluma supervisorctl status
# qq                       RUNNING
# qq-qq-acct2              RUNNING
# qq-qq-acct3              RUNNING
# snowluma                 RUNNING
```

<Callout type="info">
**Don't forget the volumes.** Declaring a HOME without mounting a volume for it means the account logs in fine but loses its session when the container is recreated.
</Callout>

### Starting one by hand from the noVNC desktop

For a throwaway account you don't want in compose, use the noVNC terminal:

```bash
mkdir -p /app/qq-temp
HOME=/app/qq-temp qq --no-sandbox &
disown
```

`disown` detaches QQ from the terminal so closing the window won't kill it. This path does not restart automatically and does not survive a container restart.

### Caveats

- **One HOME per QQ instance** — never share a `HOME` between two QQs; they'll fight over the lock file.
- **Resources**: each QQ is a full Chromium process, ~300-500 MB RAM. The default `--shm-size=1g` is fine for one; bump to `2gb`+ for multi-account.
- **All windows share the same Xvfb desktop**: noVNC shows every QQ window; minimize the ones you've already logged into. Hook keeps working regardless of window state.
- **WebUI lists every UIN automatically**: no manual configuration — SnowLuma surfaces each new account in the WebUI and `get_login_info` returns the new UINs once login completes.

## Auto-injection

The image defaults to `SNOWLUMA_HOOK_AUTOLOAD=1`: when the container starts, the hook is injected into the QQ process in passive-observe mode. Once you scan-login, the hook auto-promotes to working mode. supervisor also restarts QQ on crash through the same flow.

### Turning it off

If you prefer the legacy "manual Load via WebUI" workflow:

```bash
docker run -e SNOWLUMA_HOOK_AUTOLOAD=0 ... roozen/snowluma:latest
```

Or set `SNOWLUMA_HOOK_AUTOLOAD: 0` in `docker-compose.yml`, or edit `/app/snowluma-data/config/runtime.json` inside the volume to `"hookAutoLoad": false`. Environment variables win.

## Common ops

Shell into the container:

```bash
docker exec -it snowluma bash
```

Follow logs:

```bash
docker logs -f snowluma
```

Just SnowLuma's own logs (filter out QQ's noisy output):

```bash
docker logs -f snowluma 2>&1 | grep -v "QtNetwork\|GLib\|libQt6"
```

Browse the data directory:

```bash
docker exec -it snowluma bash -c "cd /app/snowluma-data && ls -la"
```

Edit OneBot config and restart:

```bash
# edit /app/snowluma-data/config/onebot_<uin>.json
docker restart snowluma
```

## Port remapping

If a host port is taken, just shift the host side; container ports stay the same. Example moving OneBot HTTP to host `8080`:

```yaml
ports:
  - "8080:3000"   # host 8080 → container 3000
```

Or via env (the Compose template already supports it):

```bash
ONEBOT_HTTP_PORT=8080 docker compose -f docker/docker-compose.yml up -d
```

## Building the image yourself

The build context is the main repo's `docker/` directory; the Dockerfile reads `SnowLuma.Framework.tar.gz` from it.

### From a published release

```bash
git clone --depth 1 https://github.com/Roozenlz/SnowLuma.git
cd SnowLuma

TAG=v2.4.3
gh release download "$TAG" \
  --pattern "SnowLuma-$TAG-linux-x64-lite.tar.gz" \
  --output docker/SnowLuma.Framework.tar.gz --clobber

docker buildx build --platform linux/amd64 \
  --file docker/Dockerfile \
  --tag roozen/snowluma:$TAG docker --load
```

### From a local build

```bash
pnpm install --frozen-lockfile
pnpm build:all

tar -czf docker/SnowLuma.Framework.tar.gz -C dist .
docker buildx build --platform linux/amd64 \
  --file docker/Dockerfile \
  --tag snowluma:local docker --load
```

`dist/` must contain the complete runtime layout (`index.mjs`, `native/`, `webui/`, `package.json`, …); `pnpm build:all` produces exactly that.

### Multi-arch

A local `buildx build` can only `--load` one platform at a time. For a merged amd64 + arm64 manifest, let CI do it:

- **On release**: [`release.yml`](https://github.com/Roozenlz/SnowLuma/blob/main/.github/workflows/release.yml) calls the shared `docker-image.yml` after the Release is published.
- **Rebuild a historical tag**: run [Rebuild Docker Image](https://github.com/Roozenlz/SnowLuma/actions/workflows/dispatch-docker-release.yml) manually with `snowluma_tag` — no need to re-tag.

### The QQ build baked into the image

The Dockerfile downloads the Linux QQ `.deb` from Tencent's CDN, pinned by three build args:

```dockerfile
ARG QQ_VERSION=3.2.35-54395
ARG QQ_CHANNEL=9.9.37/beta
ARG QQ_HASH=816b3c79
```

Tencent rotates both the channel directory and the content hash on every release, so stale values 404 immediately. When the build log shows `Unable to download linuxqq_*.deb`, grab the new triple from the [linuxqq PKGBUILD on AUR](https://aur.archlinux.org/cgit/aur.git/plain/PKGBUILD?h=linuxqq) and override it:

```bash
docker buildx build \
  --build-arg QQ_VERSION=3.2.36-xxxxx \
  --build-arg QQ_CHANNEL=9.9.38/beta \
  --build-arg QQ_HASH=xxxxxxxx \
  --file docker/Dockerfile --tag roozen/snowluma:test docker
```
